The dashboard editor still makes the owner work too hard.

The central problem is competing workspaces: a permanently visible widget library, a miniature dashboard and a clock inspector, squeezed beneath loosely related navigation. Removing coordinate fields helped, but the editor still behaves like a collection of controls rather than one clear editing task.

ScreenshotsElement-by-element critiqueProposed direction

What should stay

The real widget preview, staged changes, visual clock styles, direct manipulation and Apply/Discard protection are useful foundations. Preserve the warm artwork and touch targets. The next pass should fix composition and feedback, rather than add another layer of controls.

What the current editor actually looks like

Fix first

1. The widget palette is physically broken

At 1280 × 720, the palette is 116 px wide and inherits 24 px padding on each side. That leaves roughly 68 px for each card. Labels wrap, previews become scraps, and only one complete widget is visible before scrolling. Disabled, already-added widgets occupy the first positions.

Alternative. Remove the inherited card padding immediately. Then replace the permanent rail with an Add widget gallery containing generous previews of available widgets. Put already-added widgets after available choices, or let them select their existing instance.

Acceptance. A person should see what can be added without scrolling past four disabled widgets. No clipped labels or overlapping drag handles.

Fix first

2. The canvas loses the competition for space

Its allocated column is 826 px wide, but the visible canvas is only about 557 × 341 px because height is the limiting factor. Centering it leaves roughly 269 px of unused horizontal space inside that column. The three-column layout is paying for sidebars without making those sidebars useful.

Alternative. Give the canvas the main workspace. Use a temporary Add widget panel and a contextual inspector; on short screens show one tool panel at a time. Reduce the two layers of header and toolbar spacing before reducing the actual dashboard.

Acceptance. The canvas remains comfortably editable at 960 × 540 and 1280 × 720. Tool panels should earn their space and close when the task is complete.

High

3. The toolbar has no coherent grouping

Choose a layout, Pages and Household are spread across the width as if they were equal editing tools. Pages changes navigation; Household edits content. Neither label explains its relationship to arranging widgets.

Alternative. Keep Layouts and Add widget together. Move page visibility back to a clearly named navigation setting. Offer Edit content when the relevant household widget is selected, with a secondary route elsewhere in Settings.

Acceptance. Every visible toolbar action should help arrange the current dashboard or clearly describe why it leaves the editor.

High

4. Selection feels arbitrary and the inspector is inconsistent

The clock is selected on entry, so the right column immediately reads like a clock-style picker rather than a general dashboard editor. Other widgets have no comparable options beyond removal. At the primary size, Remove module falls below the inspector’s visible area.

Alternative. Start with a brief neutral instruction or restore an intentional selection. Reveal a clearly titled widget panel on selection, with relevant style/content actions and consistently accessible Remove widget. Use one vocabulary: widget.

Acceptance. Selecting each widget should produce a useful, proportionate panel. Removal must not require discovering an independent scrollbar.

High

5. Resize looks like an expand button

The large terracotta square with diagonal arrows dominates the selected clock. It resembles a fullscreen action. At 960 × 540 it occupies much of the clock’s small preview. The instruction says to drag widgets but does not visibly explain resizing.

Alternative. Use a recognizable corner grip with a generous invisible touch target, a quiet selection outline, and concise move/resize guidance. During dragging, reveal snap positions and clearly mark blocked placements. Retain an accessible non-drag path without restoring coordinate fields.

Acceptance. A first-time user can tell how to move and resize a widget. The handle should never obscure the feature being edited.

High

6. Templates obscure what they are changing

The layout popover covers the left side of the dashboard, including the selected clock. Its diagrams contain identical anonymous blocks, so Photos first and Plans first depend on their names rather than visibly demonstrating the difference. Current: Custom looks like an implementation status.

Alternative. Show real miniature compositions with recognizable photo, clock, weather and agenda content. Put the template choices beside or below an unobscured preview. Make replacement consequences explicit when the current dashboard contains additional widgets.

Acceptance. A person can compare options by looking, see the whole staged result and return to their existing layout before applying.

High

7. Adding and rearranging need visible spatial feedback

The code rejects overlapping or out-of-bounds placements and may ask the owner to make room. That is a valid constraint, but it asks the person to solve packing rules. Touch dragging begins on a separate small handle while tapping the card adds, a distinction the presentation barely teaches.

Alternative. Keep tap-to-add as a complete workflow. When a widget is chosen, highlight valid placements; if none fit, offer a reversible preview of a layout adjustment or a clearly explained replacement. Use the same visual language for drag targets and blocked resizing.

Acceptance. No silent rearrangement. No unexplained refusal. Every failed placement should offer a comprehensible next step.

Medium

8. The preview mixes viewing and editing affordances

The cloned dashboard retains weather and agenda navigation arrows, while an editing overlay intercepts the widget surface. The content looks live and clickable, but interaction means select/move. The page behind the lightbox repeats the same dashboard, particularly prominently on large screens.

Alternative. Make editing mode unmistakable through selection and hover/focus treatment. Suppress misleading in-widget navigation affordances in the editor, and soften the backdrop further. Keep real content and faithful proportions.

Acceptance. The owner should know which dashboard is being edited and should not expect a weather arrow inside the canvas to open Weather.

Medium

9. Commit and recovery are spatially detached

Apply layout and Cancel changes sit below the palette rather than near the editing outcome. Both appear disabled on entry. Recent changes appears only after edits and opens another disclosure. Existing status messages still say Save although the action is Apply layout.

Alternative. Place a stable action group at the end of the workspace: a clear completion action and a secondary cancellation path for drafts. Give recovery one understandable, contextual presentation. Make status copy match the actual button labels.

Acceptance. Saved, staged and discarded states must be clear without permanent Undo/Redo clutter or surprise prompts.

Fix first

10. Responsive behavior preserves furniture instead of usability

At 960 × 540, the canvas becomes a tiny central thumbnail, the palette shows roughly one card, and the lower clock choices are cut off. At 1920 × 1200, the palette remains narrow despite abundant space. The layout technically fits but does not adapt its interaction model.

Alternative. Choose layouts based on available editing space, including height. Short landscape needs a dominant canvas plus temporary tools; larger landscape can support a properly sized gallery or inspector. Define minimum useful canvas and card sizes.

Acceptance. Review actual tasks at every landscape size: add a widget, select it, resize, change style, remove and cancel. Absence of overflow alone is not acceptance.

A simpler editing sequence

  1. Open a large, recognizable dashboard with a short instruction and two clear tools: Add widget and Layouts.
  2. Select a widget to reveal its options. Keep the selected widget visible while changing it.
  3. Add through a generous gallery, then show where the widget can go.
  4. Drag and resize with clear snapping, blocked-placement feedback and a recoverable draft.
  5. Apply the result or cancel. Keep unrelated settings out of the arranging task.

First repair the inherited palette padding and the height-driven layout collapse. Then prototype the temporary gallery and contextual inspector together. Making the palette wider alone would squeeze the canvas further.
