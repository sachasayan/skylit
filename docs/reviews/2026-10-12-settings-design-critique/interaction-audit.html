A stricter design test

Start with the intention, not the input type.

The earlier critique gave too much weight to where controls live. The expanded analysis treats each setting as a new design problem. A dropdown does not become appropriate because it fits nicely in a row.

1. Does a decision need to exist?

If the screen size is known, match it. If the app should always make room for its editor, do not ask the owner to expand it. Remove implementation questions before designing new controls.

2. What kind of decision is it?

An exclusive choice, on/off policy, continuous value, visual arrangement, entity selection, content creation and consequential action each need different interactions.

3. Can the effect be shown?

Choose layouts from thumbnails, slideshow styles from motion examples and framing on the picture itself. Keep understandable labels alongside visuals.

4. Which state makes it relevant?

Show selection tools after entering Select mode, Stop after starting a session, and schedule parameters after enabling a schedule. Provide clear routes without permanent clutter.

5. What is the owner’s current state?

Lead with configured city, current source, disabled review, protected pictures or available update. Treat choosing, editing and automating as distinct concepts.

6. How does the interaction finish?

Define apply/cancel, progress, error, undo and return behavior. Provide keyboard and touch alternatives; a hidden gesture cannot be the only usable route.

“Optimal” is contextual, not a universal widget ranking. A segmented choice works for three modes, but not twenty-four custom collections. A brightness slider is appropriate; two crop sliders are not. Necessary credential and date forms remain forms, designed as focused tasks.

No automatic escape hatch called Advanced

Remove a choice the app can resolve. Simplify a choice with a good default. Move an activity to a real tool. Use disclosure when a legitimate task has infrequent details—not to preserve every exposed internal parameter.

Concrete alternatives for every control.

Each decision below covers the named current controls. Repeated instances share a recommendation when their function is identical. The machine-readable coverage ledger maps every inventory record to exactly one decision; no control is silently omitted.

Recommendations describe intended behavior, including cases where the current interaction should stay. They are design proposals; migrations must preserve saved values, privacy boundaries and verified service behavior.

Remove permanent action

Arrange neatly

Current: Arrange neatly

Alternative: Remove this button. Offer the visual layout templates for intentional replacement. When a widget cannot fit, explain the constraint and let the owner make room.

Why: The current action repacks everything into equal-size tiles. “Neatly” hides a substantial and potentially unwanted reset.

Contextual recovery

Undo and Redo

Current: Undo · Redo

Alternative: Remove the permanent pair from the toolbar. After a meaningful move/remove/replacement, offer a quiet Undo action while the draft exists. Keep keyboard history available; Cancel restores the saved layout.

Why: Recovery remains important, but two permanently visible editing commands do not need equal weight with composition. Do not make the only recovery route a short-lived toast.

Infer automatically

Preview screen

Current: Preview screen

Alternative: Match the current dashboard’s viewport and aspect ratio automatically. Scale that exact canvas to the available editor space. Put alternate-size checks in developer tooling.

Why: Screen geometry is known. Asking the owner to choose a testing resolution exposes our development workflow.

Remove workaround

Expand canvas

Current: Expand canvas

Alternative: Remove the button. Open arrangement in a sufficiently spacious workspace, adapting palette and inspector into temporary panels when necessary.

Why: A user should not have to repair the editor’s allocation of space. Current expansion hides tools without meaningfully enlarging the captured canvas.

One visual entry per widget

Widget palette: add and drag

Current: Add Clock & date, Drag Clock & date to dashboard, Add Weather, Drag Weather to dashboard … (18 repeated controls; all mapped in ledger)

Alternative: One recognizable card per widget with an integrated drag affordance. Tap places it in a suitable free spot; drag shows the destination before release. Already-added cards show a clear state.

Why: Two separate button identities for each widget should not become two visually competing operations. Preserve tap and keyboard alternatives to dragging.

Direct manipulation

Move and resize affordances

Current: Move Clock & date, Resize Clock & date, Move Weather, Resize Weather … (8 repeated controls; all mapped in ledger)

Alternative: Drag a widget body to move it; use a modest corner grip to resize. Enlarge invisible hit areas instead of drawing huge handles. Show snapping and invalid placement directly on the canvas.

Why: The object is the best control. Keep focused keyboard movement and resizing with concise help in an accessible support route.

Remove numeric controls

Column, Row, Width and Height

Current: Column · Row · Width · Height

Alternative: Remove all four. Drag/resize with snapping; optionally offer useful named sizes as a shortcut. Keep keyboard equivalents.

Why: These are layout-engine coordinates, not owner preferences. Hiding them in Advanced would retain the wrong model.

Visual selector

Clock style

Current: Clock style

Alternative: Landscape, Analog, Flip and Botanical thumbnails using the selected widget’s current proportions and theme. Selecting one changes the widget in place.

Why: The owner chooses an appearance. The live widget supplies the preview; a second expandable clock sample is redundant.

Contextual action

Remove module

Current: Remove module

Alternative: Show a recognizable Remove action only for the selected widget, with an accessible text label and recovery in the draft.

Why: Removal belongs to selection. It must not compete with every widget or require searching a general inspector form.

Keep transaction; simplify language

Save dashboard and Discard changes

Current: Save dashboard · Discard changes

Alternative: Stable Apply and Cancel controls. Apply appears enabled when the draft differs; Cancel abandons the draft. Leaving with a draft must offer an explicit outcome.

Why: Spatial editing benefits from experimentation. Clear draft boundaries solve this without turning the whole Settings area into a form.

Elements beyond the input inventory

The aggregate screen must also make sense.

A complete control audit still misses headings, explanatory text, previews and the relationships between them. Those determine whether the collection of good controls feels like a good product.

The 9:15 / Today on your frame / Selected palette preview

Replace with a small authentic live theme/text example whose purpose is explicit. Remove the decorative Selected palette pill. A person should know what is being demonstrated and which control changes it.

Generic Saved on this frame header

Remove the standing all-purpose claim. Immediate preferences give local feedback; task forms show drafts and explicit commits. A saved status cannot truthfully describe an unsubmitted credential or unfinished layout.

Settings and repeated section headings

Keep one modest global context and one strong current-page heading. Consistent spacing should signal section relationships, not pad every control to the same importance.

Expanders that look like headings

Use clear chevrons, current-value summaries and predictable hit areas. Large workflows open a subpage/workspace instead of growing the entire document.

Persistent technical explanations

Lead with useful state and next action. Put details at the moment they matter, with deeper help available. Keep important privacy/permission limitations visible where a decision depends on them.

Empty and unsupported states

An empty collection or disabled review queue needs a purposeful state and useful next step. Browser-unavailable native features need a clear explanation instead of an apparently operable configuration form.

Active versus inactive parameters

Do not show bright sliders, start/end times, Stop or Remove as if their prerequisite existed. Keep a summary for disabled behavior; reveal its parameters when deliberately enabled.

Tiny tool canvas surrounded by large controls

Give pictures and composition the dominant area. On short landscape screens move secondary tools into temporary panels; primary action, current mode and return route remain stable.

Decorative previews versus useful demonstrations

A preview should answer “what will change?” and use the actual theme, aspect ratio, selection or motion. Do not add another card simply because a settings page has empty space.

Close, Back and category navigation

Keep Close stable and clearly named; Back returns within Settings without discarding context. Restore focus to the control that opened a tool. Category changes must handle unfinished drafts deliberately. On short screens, category navigation remains reachable rather than sharing an ambiguous scroll region with the content.

Accessibility and touch

Visible checks and focus must work in all theme pairs. Every drag has a keyboard/tap alternative; every icon has a name; every hidden command has a discoverable route. Preserve generous hit areas and reduced-motion precedence.

Quality bar for the next design

Judge the alternatives as complete interactions.

  1. Understand before opening: mode choices are visible; layout thumbnails convey structure; slideshow examples convey motion; the configured city/source is explicit.
  2. No development questions: the owner does not select test resolution, edit grid coordinates, tune crop axes or paste serialized preferences.
  3. No ambiguous commands: replacement is labeled as replacement, removing is scoped, and a button’s effect is predictable before it is used.
  4. One mode at a time: normal photo viewing, bulk selection and photo editing have distinct behavior. Switching mode makes the next action obvious.
  5. Control-state coherence: no meaningless Stop, empty-list Delete, inactive schedule parameters or healthy Retry. Defaults and overrides are visible.
  6. Useful recovery without a busy toolbar: experimental changes are reversible; Apply/Cancel remain clear; Undo is discoverable when relevant and does not vanish as the sole recovery route.
  7. Outcome feedback: every change shows its effect or state. Native tasks have progress and a verified result, rather than a generic success message.
  8. Intentional responsive composition: verify the actual frame and multiple 16:9/16:10 sizes, especially short screens. More width must not merely create wider forms.

The revised direction

Rebuild the interaction model and information architecture together. Start with the dashboard, photo library and basic appearance choices because they demonstrate the largest mismatch. Carry the same decision-by-decision standard through every destination.

Evidence: the 46 synthetic captures in the main report, earlier editor captures, the complete DOM inventory, and source inspection of current behavior. Hidden legacy controls are explicitly reviewed. These are design judgments, not claims of frame acceptance testing.
